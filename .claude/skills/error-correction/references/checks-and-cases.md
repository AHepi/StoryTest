# Checks and kept cases

Open this when you write or change a check, when the commit gate stops a commit, or when you run the kept cases.

Contents: 1 A check is an explanation too. 2 The machine checks and the commit gate. 3 Writing or changing a check. 4 The kept cases. 5 Running the kept cases. 6 When a kept case fails. 7 Traps.

## 1. A check is an explanation too

**Case.** The map checker reported "0 problems" after every change from log entry 17 onwards. An audit then planted six faults in a copy of the repository, and it caught one. Two of the faults it missed: a module's name hiding inside a longer word ("myth.md" inside "mythic family"), and a row missing from the map table while the file was named in a different table. It also ended the same way whether it found problems or not, so nothing could use it as a gate.

**Point.** A check says, in effect, "if this were wrong, I would see it". That is an explanation, and it is measured like one. A check that would pass whatever the files were like holds nothing in place. So every check is run on the thing it is meant to catch and on that thing's nearest innocent neighbour, and the planted faults are kept, so that they are rerun whenever the check changes. Its "0 problems" is then worth something. (hard-to-vary's `testing-against-cases.md`, section 1, says the same of any test.)

## 2. The machine checks and the commit gate

All of them run from `.claude/skills/error-correction/scripts/run_all_checks.py`:

| Check | What it catches | Script |
|---|---|---|
| Frozen files | A changed, missing or unlisted frozen file (any file in `sources/` but README.md, and all of `foundations/`); a path listed twice; a line removed or changed on the fingerprint list | `check_frozen_files.py` |
| Maps | A module missing from its skill's map table or diagram; a path or "section N" pointer that lands nowhere, or points into another skill without naming it just before; a description over the length limit; a shared passage that differs between copies, or is missing from a file its markers name | `add-source/scripts/check_maps.py` |
| Records | An old log entry rewritten; a correction note that points to no later entry; a numbered line inside an entry that is not indented; a status line older than the last entry; README missing a file or folder; a question or correction with no status; a skill or kept case resting on an answered question without saying so beside that question's number; a write-up with no "Checks run on these notes" | `check_records.py` |
| Owner quotes | A quotation of an owner theory in the term sheet, curly or straight, that is not word for word, or is credited to the wrong theory | `check_owner_quotes.py` |
| Allowed titles | A line on the copying check's allowed list that is not an author or title named in the source register | `add-source/scripts/overlap_check.py --check-allowed-list` |
| No book files | A book text, ebook or large text file in the files to be committed | `run_all_checks.py` |
| Copying from books | A run of 8 or more words shared with a book, in any file with a text ending (`.md`, `.txt`, `.py` and the others the check lists), unless no more than 2 of its words fall outside an allowed title or name; NOT RUN where the book texts are absent | `add-source/scripts/overlap_check.py` |

Each is reported as passed, FAILED, NOT RUN, or COULD NOT RUN (the check's own script broke). Could not run stops a commit like a failure does.

**The commit gate** (`.githooks/pre-commit`, and `.githooks/pre-merge-commit` for a merge commit) runs `check_commit.py`. Git runs it by itself before every commit, in a copy where the gate is switched on. When it passes a commit, `.githooks/prepare-commit-msg` stamps the commit's message with a line "Workshop-gate: approved <tree>", naming the exact contents it passed. The last approved commit is found by walking back along the main line (from the last commit to its first parent, and so on): the first commit that is approved. A commit is approved if its stamp matches its own contents, or if it is a merge made without the gate that is exactly git's automatic merge of its two parents (GitHub's merge button makes such a merge when there is no conflict), when one parent is approved and the other is approved too, or is from before the gate and already inside the approved one's history, and the two did not both change the checks. When both changed the checks, nobody has tested them together, so the merge is not counted, and the next commit runs the last approved commit's planted-fault test on them; a correction then goes through the same way. A git older than 2.38 cannot make git's automatic merge on its own (`git merge-tree --write-tree`): with one, no merge made without the gate is counted, and a merge through the gate asks for a receipt for its whole change. Normally the last approved commit is simply the last commit. A merge made on GitHub with a conflict resolved by hand is not approved, so the walk goes on to its first parent, the main line. The gate takes the checks from the last approved commit, never from the files being changed, and compares the files with it, so a check cannot be loosened in the same commit as the work it would stop. Then it:
- runs every check on a copy of exactly what is staged, reading the frozen files from git's staging area for this commit (the one `git commit -a` or `git commit <file>` makes for itself, when it does), and comparing the log, the frozen list and the source register with the last approved commit; in a merge, the log entries the other side added since the two lines of work split must be kept too, by number and text;
- checks the review receipt (`review_receipt.py`) for this commit's own change; for a merge or a pull, only the merge's own changes need one (anything beyond the automatic merge of its parents), since the commits it brings in carry their own;
- refuses a change to, or the deletion of, a review receipt the last approved commit has: receipts are only ever added to;
- looks again at the commits since the last approved one (`recheck_commits.py`, below), and at the commits a merge brings in;
- when this commit's own change touches a check, a hook, the allowed-titles list or the settings, refuses it mixed with other work (apart from its receipt, the project story, the corrections file and the source register); and whenever the staged checks differ from the last approved commit's, runs that commit's planted-fault test on them, and the changed test too.

**Commits made without the gate** (with the gate skipped or switched off, a `git revert`, rebase or cherry-pick that goes through without a conflict and changes the contents, a merge made on GitHub with a conflict resolved by hand, a commit made on GitHub) carry no matching stamp. What they got wrong in the files themselves, a frozen theory edited, an old log entry rewritten, a receipt deleted, is judged at the next commit through the gate, against the last approved commit and with its checks: it stops that commit until a commit puts it right, and a commit that puts it right clears it. A check such a commit loosened is different: it is judged only by the last approved commit's planted-fault test and by its own late review, the same limit as for a loosened check across two commits (below). Once a commit through the gate is approved, every commit before it is settled. A revert, cherry-pick or merge that stops for a conflict and is finished with `git commit` or `--continue` runs the gate like any commit; a rebase finished with `--continue` does not.

**The recheck** (`recheck_commits.py`) runs before every commit and at session start. It looks only at the commits since the last approved one, for what only the history can show: each one's review receipt, if it changed a reviewed file; a receipt that says the change was withdrawn, believed only if the files show it withdrawn; a book file added, even if later removed; and a change to the gate's own files. A missing or false receipt stops a commit, and a new commit can put either right. A book file or a change to the gate's own files is a note, not a stop, and a note is shown only until a commit through the gate is approved. So after a pull, a rebase, a cherry-pick or a merge made mid-session, run `recheck_commits.py` before the next commit. Copy each note into the log entry of the commit you are about to make (or, if a note is first seen in the output of a commit that has already passed, into the next entry) and tell the owner, who decides what to do: look at a change to the gate's files, or remove a book file from the history, which only rewriting the history does.

A receipt's name is its fingerprint, made from the lines a change adds and removes and the one unchanged line either side of each. So a rebase or cherry-pick that leaves the change and those neighbouring lines as they were finds the receipt it already has; one that lands next to an edit made meanwhile, a line moved after its review, or a squash that joins several changes into one, needs a new review.

**Two lines of work that each add log entries**, two sessions say, meet when one is merged into the other. Keep the main line's entries under their numbers and number the other line's new entries after them. After a merge made on GitHub, the next commit is judged against the main line, so that resolution goes through, and renumbering the main line's entries is stopped. A merge made through the gate keeps both sides' new entries by number and text, so when both added the same number it is stopped, with a message: abort it (`git merge --abort`) and rebase your branch onto the other line instead (`git rebase <the other branch>`), numbering your new entries after its. GitHub's "Resolve conflicts" editor and its "Update branch" button merge the other way round: they merge the main branch into the session's branch, so the session's branch is the first parent, and the gate then judges against the session's side. If you carry on from such a branch, the natural resolution is stopped, and the advice to put the entry back would copy the session's entry over the main branch's approved one: do not follow it there. Rebase the session's branch onto the main branch instead, numbering its entries after the main branch's (which needs a force-push), or do not carry on from that branch.

Two exceptions, each printed when it applies. The one commit that first brings the gate in has no earlier version, so it is checked by the checks it brings. And a commit made straight on top of an approved commit that changes only checks, with nothing else but new review receipts (files named by a fingerprint), is checked by its own changed machine checks, so that a wrong one can be corrected even when it stops every commit; its receipt is still checked by the last approved commit's receipt check, the last approved commit's planted-fault test judges the changed checks, and its log entry follows in the next commit. This exception does not reach the receipt check, the recheck, the planted-fault test or the gate script itself: see "When a check is wrong", below.

The session-start hook switches the gate on with `git config core.hooksPath .githooks` and says the gate is on only if the gate's files on disk match the last commit's. It runs the machine checks the gate will use, those of the last approved commit, compared with that commit, and prints the lines under anything that fails. It does not run the planted-fault test, which takes minutes, so a check changed without the gate can still stop the next commit there. It runs the recheck: how many commits there are since the last approved one, the problems in them to put right, and the notes for a person. It also lists every planted test retired so far. To switch the gate on by hand, run that same command once in the repository folder. If python3 is missing, the gate stops the commit rather than letting it through unchecked; if the gate script itself breaks before it finishes (a typo, say), pre-commit says so in a plain line.

**What the gate cannot do.** The gate stops most honest mistakes and shortcuts, by itself. Among what it does not stop (each is said where it applies, and this list holds those known so far):
- An agent set on getting round it. The gate is made of files in the repository: git runs `.githooks/pre-commit` from the disk, and that runs the gate script as it is in the last commit, whether or not the gate approved that commit. Whoever edits those files, or types a stamp by hand, can get past it; the recheck and session start would see some of it, and a determined agent could hide from them too.
- A change to the gate's own files made outside it (on GitHub, say): it runs in its changed form, whether or not it was meant to loosen anything, and is only noted for a person.
- A loosened check, across two commits: the commit that loosens it, whether made through the gate or without it, is judged only by its review (on trust) and by the planted faults that exist; once a commit carrying it is approved, the commits after are judged by the loosened check.
- Copying: close paraphrase of a book, which no script sees even with the books present (the copy-checker reads for it, on trust); a copied passage added and removed between two commits through the gate; and small text outside the skills while the books are absent. The copying check reads the files as they are at each commit, and only where the books are present.
- What a receipt says. The gate checks a receipt's form: whether the named reviewer really ran, whether a light receipt was rightly judged light, and, with the books absent, what its "Book text" line says, are the maker's word. "The owner named first" for a retired test is checked as a name.
- The other line's log entries after a merge made on GitHub with a conflict: the next commit is compared with the main line only, so the other line's entries are kept word for word on trust.
- A copy whose history is cut short (a shallow clone): the gate may find no approved commit, and then compares with the last commit; it says so, and `git fetch --unshallow` puts it right.
- Settings kept outside the repository (the local settings file Claude Code keeps beside `.claude/settings.json`, or a person's own settings) can switch the workshop's hooks off; no check here reads them.
- A note for a person (a change to the gate's own files, a book file left in the history) is shown only until the next approved commit: acting on it is on trust, with the log entry as the trace.
- An approved commit rebased with its contents unchanged keeps its stamp, so the commits it now sits on, which the gate never saw, are settled unseen: after `git pull --rebase`, a book file uploaded and deleted on GitHub, or a change to the gate's own files made there, is never noted. To see them, run `recheck_commits.py` in a fresh clone of the pulled branch, before your own commits are rebased onto it.
- A pull request merged with GitHub's "Rebase and merge" and later reverted on GitHub: neither side was approved, so the log entries and receipts it added and the revert removed are never compared. Merge pull requests with a merge commit.
- GitHub's own conflict merges and "Update branch" make the session's branch the first parent (the paragraph on two lines of work, above, says what to do).
- A merge made on GitHub whose main side holds commits from before the gate that the approved side lacks is not counted as approved; if no approved commit lies behind it on the main line, the gate compares each commit with the last one, as for a shallow copy, so a frozen edit or a log rewrite made after it would pass. Before a pull request that brings the gate in is merged, merge the main branch into its branch through the gate, so that the main side is inside the approved side and the landing counts.
Only a check that runs outside the repository (owner question S10) or the owner can catch everything. Not yet tried on Windows itself: `.gitattributes` keeps the hooks and scripts with Unix line endings, and a copy made with Windows line endings on Linux commits through the gate.

**When the gate stops a commit**, the stop is a sign (the skill's loop, step 1), but not a tripwire, and it is written down nowhere of its own: the change that puts it right, and that change's receipt, are the record. Usually the check is right: put right what it found, and commit again. The exception is a stop that finds what a commit made without the gate got wrong in the files: a frozen theory edited, an old log entry rewritten, a receipt deleted, a check loosened. That error got into the history past the stages meant to catch it, which is a tripwire (the skill's "How much to do"): record it as a correction, naming how the commit got past the gate, and put it right with a new commit. A stop that only asks for a late receipt (after an owner's edit on GitHub, or a rebase next to an edit made meanwhile) is not one. A frozen file goes back as the commit the gate's message names has it (`git checkout <that commit> -- <file>`: the most recent commit that still has the text on the frozen list); if the owner meant to revise it, the revision is stored as a new file through the add-source skill, and the frozen text still goes back. A rewritten log entry goes back by itself: copy the entry's text from the last approved commit (`git show <that commit>:"StoryTest - project story.md"`) over the rewritten one, keeping everything added since; never put back the whole file, which would drop entries added since. A receipt deleted by a revert goes back with `git checkout <that commit> -- <receipt>`. A missing receipt is written late (`review_receipt.py new --commit <commit>`, reviewed, then committed); an edit made on GitHub that changes no meaning gets a light late receipt. If the late review does not pass, take the change back out: `git revert --no-commit <commit>`, put back any receipt the revert took out, and commit through the gate. The withdrawal is itself a change and needs its own receipt, full unless the withdrawn change itself changed no meaning; the late receipt for the withdrawn commit says "not passed (withdrawn in this commit)", and the recheck believes it only if every line that commit added is gone, every line it removed is back, and its change can no longer be undone from the files. If the late review passes only part of the commit, take the rest out by hand in a commit through the gate, with its own receipt, and write the late receipt as passed for what stays, naming in its findings what was taken out and where. Never write a verdict the reviewer did not give. On GitHub, merge a pull request with a merge commit, not by rebasing (see "What the gate cannot do"); a squashed commit is approved only if its stamp matches its contents, and otherwise needs a receipt of its own, as does a squash made locally.

**When a check is wrong**, the check is the target. Which route clears it depends on which part is wrong:
- A machine check (one `run_all_checks.py` runs) approved by the gate: correct it in a commit that changes only checks, made straight on top of the last approved commit, with a planted fault showing the corrected check catches what it should and passes what it should. If the last commit is not approved (after a merge made on GitHub with a conflict, or a commit made there), make a branch from the last approved commit, which the gate's note names (`git checkout -b <branch> <that commit>`), correct the check there, then merge the main line into that branch through the gate and carry on from it; a merge the other way is judged by the wrong check. Any planted test that no longer fits is retired in the receipt, and a guarded one (any but the maps' and the owner quotes') only with the owner named first as reviewer, so the owner must be at hand.
- The receipt check, the recheck or the planted-fault test, approved by the gate: the same commit, but these parts judge it in their approved form. If one of them stops its own correction and no retirement clears it, the owner has two ways, and the agent prepares the exact change for either: correct the gate script itself (next item), for example so that it takes that one part from the staged files for one commit; or take the branch back to before the approved commit that brought the fault in (`git reset`), which drops the work since, to be made again. Tell the owner what is stuck, why, and what each way costs.
- The gate script itself (`check_commit.py`): git runs the last commit's copy, so a correction takes effect as soon as it is in the last commit. Prepare the exact corrected file and tell the owner; the owner commits it outside the gate, for example by editing the file on GitHub, and it is brought in with `git pull --rebase`, which runs no gate (a rebase settles the commits it lands on unseen, so run the recheck in a fresh clone first: see "What the gate cannot do"). (Not yet tried: a plain pull into a branch that has moved on makes a merge, which the broken gate script would judge.) The next commit through the gate then needs late receipts: for the correction, and, if the break came from a commit made outside the gate, for that commit too.
- A check loosened or broken in a commit made outside the gate is not used until a commit through the gate is approved on top of it, and that commit runs the last approved commit's planted-fault test on it. Put the check back, or correct it, with late receipts, as above.
Do not get round the gate unasked. A Claude hook refuses the usual ways round the gate (`--no-verify`, moving git's hooks elsewhere, deleting or overwriting the gate's files, writing the gate's records in `.git` by hand); it catches the usual spellings only.

**Not run is never passed.** Where the book texts are absent, the copying check prints NOT RUN, and the review receipt must say what book text the change adds.

## 3. Writing or changing a check

1. Say what error it catches, as a failure you can plant, and which past error it would have caught (from the corrections file). If another check already catches it, say what each one guards against that the other does not, or merge them.
2. Give it plain words and a note at the top saying what it does. It exits with code 1 on any problem and 0 on none, and prints each problem as a sentence the owner could follow.
3. Add its planted faults to `test_checks.py` (the commit gate's own tests are in `test_the_gate.py` beside it, which `test_checks.py` runs). Plant the fault it must catch, taking the real historical text where one exists, and an innocent neighbour it must let pass. Then plant the ways round it, not only the fault it names: a second route to the same fault (a second list line for an edited file), the check loosened in the same commit, a form field that accepts its own hint, a file or folder it never reads, a commit it never sees. Say what the check must print, so a fault is caught for the right reason. Run the new tests on the old check too: a test that passes on the old check as well shows nothing new (correction C15). One way: copy the last commit to a scratch folder (`git archive HEAD | tar -x -C <folder>`), put the new `test_checks.py` into it, and run it there.
4. Run `test_checks.py`, and run the check on the real repository. Any problem it reports there is either a real error (open a correction) or a false alarm (the check is not ready).
5. A change to a check goes in a commit of its own, with a full review receipt (never a light one). The skill text that describes the check (this module, CLAUDE.md's table) cannot come in that commit, so it follows in the next one; say in the log that the description lags by one commit. The gate runs the last approved commit's `test_checks.py` on the changed check, so every fault the old check caught must still be caught. A test that no longer fits is named in the receipt under "Tests retired", with why, and changed or removed in `test_checks.py` (or `test_the_gate.py`, for the gate's own tests) in the same commit, so it is not named again at the next change to a check; a test that could not run is never retired. The gate reads retirements from every receipt added since the last approved commit, so one made on a branch still counts after a merge or a rebase. Every test but those of the maps and the owner quotes guards the gate, the log, the frozen files, the receipts, the books or the hooks, and is retired only with the owner named first under "Reviewed by": tell the owner, in plain words, which guard the workshop would lose and why, and let them agree or not. Session start lists every test retired so far. The changed check takes effect once a commit carrying it is approved.

## 4. The kept cases

`kept-cases/` holds short story problems. Each one carries what a good answer **must** do and **must not** do, and each item is tied to a line of an owner theory or, where no theory speaks, to a named past error. They were written before any run, by an agent that had read the theories and the error history, not the skills, so that no skill's own example could be the answer key. Most are aimed at an error the workshop really made. One has "nothing important is wrong" as its right answer, so the skills are also tested for inventing faults. One is marked "expected to fail" until the workshop can compare two drafts.

They are the stated occasions on which "still working" is checked (Part XI of the foundation: what a change must protect is declared over stated occasions). What they cannot show: that a skill gives good advice in general. A case written with the answer in mind shows that the skill runs on that case. And every grader is the same kind of model as the answerer.

**Adding a case.** Write it before running anything on it: the writer's problem, the must and must-not lists with their grounds, and the open points that must not be graded (owner questions still open). Keep it apart from the skills: a skill's wording or example must never tell the same story or reach the same conclusion as a kept case. A new case is itself a change and needs a review receipt.

## 5. Running the kept cases

**When:** after a change to a skill, run that skill's cases; before a large change is called done, run them all. The session-start hook and the records check say which skills have changed since their cases last ran. A change that alters no meaning (a typo, a link) needs no rerun: before committing it, add a line to `kept-cases/runs.md` saying which change it was and that the cases were not rerun, with the line that `check_records.py --fingerprints <skill>` prints. It updates only that skill. If the skill was already owed a rerun, it refuses: write the runs.md line without a fingerprint line, and the skill stays listed, so that notice is never cleared by a typo. The error-correction and add-source skills have no kept cases and need no line.

**How:** `kept-cases/README.md` has the steps and the workflow script. In short:
- Start from a clean, committed state (`git status` shows nothing), and note the commit.
- A fresh agent gets only the writer's part of each case. It answers with the workshop's skills, as a session would, and also returns a stall report: where it stalled, improvised, found rules at odds, or met a stale record.
- A `case-grader` agent grades each answer against the must and must-not lists. Each batch includes at least one planted wrong answer, and the grader must fail it.
- Record the results as they came in `kept-cases/runs.md`, with the commit and each skill folder's fingerprint. A failure is never replaced by a later pass; the rerun is added below it.
- Every stall is a sign. Stalls that repeat across cases, or that point at a skill step, go through the loop.

## 6. When a kept case fails

A failure shows only that the skill, the answering and grading set-up, and the case as written cannot all be right (the thing, the rig and the inputs). Which to change is a new guess: write the three as rival guesses before changing anything (the loop's step 3). A grader can misread; a case can ask for more than its grounds support. Never change a case and the skill it tests in the same commit, and never change a case to make a skill pass: a changed case is a new case, recorded as one.

**A case whose open point is answered.** When the owner answers a question a case lists among its open points, the case no longer tests what it was written for. Keep it as it was run, and have an agent that has not read the skills write a new case that grades the answered point, in a commit separate from the skill changes. The records check lists every kept case that cites an answered question, or one being rechecked, as a note naming only its file and line: it never fails a kept case for it, since a kept case is never changed.

## 7. Traps

- **A check nobody has seen fail.** Plant the fault.
- **A planted fault caught for the wrong reason.** A test that only checks the exit code can pass because something else failed. Say what the check must print.
- **Reading NOT RUN as passed.** It says nothing about what an unrun check would find.
- **Weakening a check to get a commit through.** That is getting round it, done slowly.
- **Teaching to the test.** A case's must-list copied into a skill turns the case into an answer key. Agents that write or change the skills never see the cases.
- **Counting passes.** "10 of 11 passed" is not a warrant. Report which failed, why, and what the stalls say.
